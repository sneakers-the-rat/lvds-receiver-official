`created_at <= 1793780974`).
Headline, for the project scope defined below:

| scope | agents | usage rows | input tokens | output tokens |
|---|---|---|---|---|
| chat tree (main chat + its subagents) | 18 | 117 | 117,339,932 | 550,188 |
| checkpoint cron (`pdlvds-progress`) | 48 | 34 | 15,914,052 | 116,416 |

**Gross total: 133,920,588 tokens processed.** Read the semantics section

full context is re-sent on every model request, so the sum counts the same
content many times. It is a work meter, not a content size and not a bill.

## Files

- `token_series.csv` — one row per usage record (timestamp, agent, input,
  output, running cumulative totals), sorted by time.
- `agents.csv` — every agent in scope, its role, and its totals.
- `commit_alignment.csv` — every commit in this repo's HEAD history with
  cumulative project tokens at the commit's time and the board state from
  the audit file committed at that revision (`not recorded` where the
  record doesn't say — never back-filled).
- `progress_vs_tokens.svg` — cumulative tokens vs unconnected nets and
  clearance violations at the board-bearing attempt commits.
- `token_per_message.svg` — per-message gross tokens over time (top
  panel, log scale, colour-coded by scope) with project epochs annotated,
  and below it the cumulative tokens as a six-layer stack: each scope
  keeps its top-panel hue (main chat / subagents / checkpoint cron),
  the darker shade of a hue is input tokens and the lighter shade is
  output tokens, a scope's two layers sit adjacent so its band height
  is its cumulative subtotal, and the top edge of the stack is the
  grand cumulative total. All plotted times are Pacific time
  (America/Los_Angeles) — the CSVs keep epoch seconds, so this is
  display-only. Embedded in the site's Token usage section. Generated
  by `make_token_chart.py` from `token_series.csv` + `agents.csv`;
  each epoch in the script names the commit its timestamp comes from,
  and the script asserts the stack's per-scope layers and grand total
  against the CSVs before writing the SVG.
- `align_commits.py` — regenerates `commit_alignment.csv` from
  `token_series.csv` + git history (runs anywhere the repo is cloned).
- `api_rates.json` — hand-maintained API list prices (USD per MTok) for
  the three providers in the cost summary, each with its official
  source URL and the date it was fetched. Re-check before regenerating.
- `cost_summary.csv` — per-provider, per-scope list-price equivalents
  computed from `agents.csv` totals at the rates in `api_rates.json`
  (see the Cost summary section below). Generated by
  `make_cost_summary.py`, which cross-checks its totals against
  `token_series.csv`.

## Source

The Muse runtime database (`muse.db`, read via the read-only SQL tool).
Two candidate tables exist:

- `agent.token_usage` (per-request) — **completely empty (0 rows). Do not use.**
- `agent.agent_message_token_usage` — populated; the only source used here.
  Columns: `agent_id`, `message_id`, `input_tokens`, `output_tokens`,
  `created_at` (seconds epoch, UTC).

## Semantics — what a row is

Evidence gathered while building this export:

- A row aggregates **all model requests made while producing one message**
  in that agent. The main agent has 97 rows in this snapshot, one per
  delivered message/turn, with per-row input from ~0.09M to ~3.7M tokens
  (a turn with many tool calls makes many requests, each re-sending the
  context — hence rows larger than the 350k context window).
- Every **completed subagent has exactly one row**, timestamped at its
  completion, totalling its whole run (e.g. the CI-fix rounds 1–2 worker:
  9,121,511 input / 45,386 output in a single row).
- **Running agents have no rows.** At snapshot time the second build
  coordinator (~5.5 h of v6/Freerouting work) and this metrics worker had
  none — their usage lands only when they complete. All totals here
  therefore *undercount* in-flight work.
- Sanity anchor: one live request of the root agent on 2026-11-04T07:58Z
  was estimated at 219,814 input tokens (session status) — a single
  request, vs 49,411,439 cumulative input over its 97 message rows.

## Scope — who counts

(a) **Chat tree.** `agent.agent_ancestors` for root agent
`4925d244-018c-4b4f-9fad-7b3ad78af7c1` (this chat): 17 agents — root, 13
direct children (2 build coordinators, CI-fix ×3, gallery ×3, CI speed,
CI-signal ×3, this worker), 3 grandchildren (coordinator #1's workers).
Cross-check: `agent.subagent_spawns` lists exactly the same 13 direct
children of the root and the same 3 children of coordinator #1 — the two
records reconcile completely, no gap.

(b) **Checkpoint cron.** The `pdlvds-progress` job (every 30 min) runs
under the goal scheduler, a different tree. Found via
`scheduler.jobs`/`scheduler.job_runs`: 23 runs, each with a worker agent
and a history agent (46 ids). Usage rows exist for all 23 history agents
(the checkpoint authors, 0.39M–1.17M input each) and for 9 of the 23 run
agents (small rows, ~0.05M–0.07M); the other 14 have no rows.

(c) **Nothing else.** A prompt-text census (`subagent_spawns` prompts
mentioning the project) found no project agents outside (a)+(b).

The two scopes are disjoint agent-id sets (verified), so the total does
not double-count. Two honest overlaps of *effort*, not of records: the
root agent's rows include the turns that delivered checkpoint handoffs in
this chat (orchestration cost), and they include turns spent reading
subagent reports.

## Caveats

- The table is **live**: the root agent keeps accruing rows. This snapshot
  ends at the 2026-11-04T08:29:34Z row; later exports will be larger.
- Coverage starts at the first row, **2026-11-03T18:34:31Z**, ~6 minutes
  after the project's first user message (18:28Z) — that first row
  aggregates the opening work burst (2,945,917 input), so coverage is
  effectively from the start.
- Because subagent rows land at completion, token growth appears in lumps
  at delivery times. `commit_alignment.csv` assigns a commit the
  cumulative total of rows timestamped ≤ the commit time: work that was
  in flight at commit time is missing from that row and appears later.
- GitHub's server-side merge commits are not in this clone's HEAD lineage
  and carry no content changes; the alignment covers the 110 content
  commits of the lineage.
- Board state is parsed from the audit file **as committed at each
  revision** (an attempt-specific `results/audit-*.txt` when the commit
  touched one, else `results/pcb-audit.txt`). No ERC report is committed
  anywhere in the history (ERC reports live in CI artifacts), so
  `erc_errors` is `not recorded` throughout — the ERC story (875 → 0) is
  in `docs/00-status.md`, not in git.

## Cost summary (list-price equivalents)

Subscriptions are different for all three providers and unquantifiable
from any record available here. This project ran on a Muse
subscription — the user's known flat cost — and no per-token charge is
exposed in any record. The figures below are therefore **rough cost
estimates for if one would want to scale up**: the recorded token
volume priced at each provider's published pay-as-you-go API list
rates. They are not a bill, and not what this project cost.

Why API prices are the comparison currency (project owner's framing,
2026-11-04): Anthropic's and OpenAI's subscription tiers carry no
token count at all — Anthropic's are flat multipliers (5×, 20×) of an
undefined base amount, and OpenAI's are similar, except that hitting
the limit degrades your thinking level first. Only Muse's
subscription tiers correspond to an actual token count. A
subscription therefore cannot answer "what would this workload cost
to run as a business"; the pay-as-you-go API rates can, which is why
this table uses them. The cached-vs-uncached input split is what
makes the estimate realistic rather than an upper bound — see the
input-split estimate (`input_split.csv`), which replaces the assumed
cache share used in the sensitivity line below.

Rates used (USD per 1M tokens, standard rates, fetched 2026-11-04;
also in `api_rates.json`):

| Provider / API | Model | Input | Cached input | Output | Source |
| --- | --- | ---: | ---: | ---: | --- |
| Meta — Muse (Meta Model API) | `muse-wonder-1.0` (Standard) | $4.00 | $0.20 | $20.00 | [dev.meta.ai/docs/pricing-rate-limits](https://dev.meta.ai/docs/pricing-rate-limits) |
| Anthropic — Claude API | Claude Opus 5.5 | $4.00 | $0.20 (cache read) | $20.00 | [platform.claude.com/docs/en/about-claude/pricing](https://platform.claude.com/docs/en/about-claude/pricing) |
| OpenAI API | GPT-6 Astra (Standard) | $10.00 | $1.00 | $50.00 | [developers.openai.com/api/docs/pricing](https://developers.openai.com/api/docs/pricing) |

Tier choices: Muse Wonder is the model family that actually served
this project (below), priced at Meta's own published Model API card.
Claude Opus 5.5 is Anthropic's flagship tier for long-running agentic
coding — its pricing page's own description — the tier an agent run
like this one would use (one tier sits above it, Claude Fable 5.1 at
$10 / $50 / $0.25). GPT-6 Astra is OpenAI's flagship model.

Cost of the recorded volume (133,253,984 input + 666,604 output
tokens; input billed at the standard uncached rate; totals to the
nearest dollar; snapshot 2026-11-04T08:29:34Z):

| Scope | Input | Output | Muse | Claude | OpenAI |
| --- | ---: | ---: | ---: | ---: | ---: |
| Main chat | 51,605,352 | 141,610 | $209 | $209 | $523 |
| Subagents | 65,734,580 | 408,578 | $271 | $271 | $678 |
| Checkpoint cron | 15,914,052 | 116,416 | $66 | $66 | $165 |
| **Total** | **133,253,984** | **666,604** | **$546** | **$546** | **$1,366** |

The Muse and Claude totals are identical because the rate cards are:
Meta lists `muse-wonder-1.0` at exactly Opus 5.5's prices. Per-scope
detail to the cent is in `cost_summary.csv`.

Cache sensitivity (one line per provider, **assumed** share — the
measured new-vs-repeated estimate lives in `input_split.csv` when
present): if 95% of input tokens had been billed at each provider's
cache-read rate instead of the standard rate, the input line would
fall from $533 to roughly **$52** on Muse and on Claude (total
≈ $65), and from $1,333 to roughly **$193** on OpenAI (total
≈ $227). Cache *write* charges, where a provider has them (Anthropic
1.25×/2× of base input; OpenAI 1.25× on this model), are not
modelled, so a real cache-heavy bill would land between the headline
and the sensitivity figure.

Why even these equivalents are rough:

- **Model attribution.** `agent.agents.model` is populated for all
  66 project agents, but only with internal codenames: 49 root agents
  (this chat's root plus the 48 checkpoint-cron run roots) record
  `ipnext/watermelon-v0`, and the 17 subagents record
  `ipnext/avocado-5.17-v1`. No Anthropic or OpenAI model name appears
  in any project record; transcript session headers carry no model
  field, and `runtime.requests` has no model column at all. The
  runtime identifies this chat's model as Muse Wonder. So there is
  no evidence any project agent was served by a non-Muse model —
  the Claude and OpenAI columns are equivalents for comparison, not
  records of spend.
- **Steering context.** Meta's Model API token counts exclude
  Meta-injected steering context (it is not billed); the local
  records this table is built from may include injected context.
- **OpenAI long-context pricing.** Prompts over 272K input tokens
  bill at 2× input/cache and 1.5× output for the full request on
  GPT-6 Astra. This project's recorded turns include per-message
  input aggregates well above that, but the aggregates cannot
  separate individual request sizes, so the headline uses standard
  rates throughout; an identical workload actually billed by OpenAI
  would cost more than $1,366.
- **Tokenizer differences.** Anthropic's pricing page notes its
  current tokenizer produces roughly 30% more tokens for the same
  text than its predecessor; the counts here were metered on Muse,
  so identical text would meter somewhat higher on Claude.

## Regenerating at project end

CI cannot reach this database. An agent with `muse.db` access re-runs the
SQL below, rewrites `token_series.csv`/`agents.csv`, then runs
`python3 metrics/align_commits.py .`, re-renders the progress chart from
`commit_alignment.csv` (attempt commits only), and re-renders the
per-message chart with `python3 metrics/make_token_chart.py .`. Re-check the rates in
`metrics/api_rates.json` against their source pages, update rates and
fetch dates together, then run `python3 metrics/make_cost_summary.py .`.
Update the snapshot date and totals in this file and in
`docs/00-status.md`.

### SQL used for this snapshot (verbatim)

Token-table check:

```sql
SELECT (SELECT count(*) FROM agent.token_usage) AS token_usage_rows,
       (SELECT count(*) FROM agent.agent_message_token_usage) AS msg_rows
```

Tree census:

```sql
SELECT descendant_id, distance FROM agent.agent_ancestors
WHERE ancestor_id='4925d244-018c-4b4f-9fad-7b3ad78af7c1'
ORDER BY distance, descendant_id
```

Spawn cross-check:

```sql
SELECT child_agent_id, child_depth, status, created_at
FROM agent.subagent_spawns
WHERE parent_agent_id='4925d244-018c-4b4f-9fad-7b3ad78af7c1' ORDER BY created_at
```

Per-agent totals with verification bound (the bound is this snapshot's
last row; the exported CSV was verified to reproduce these sums exactly,
per agent, all 47 agents with rows):

```sql
SELECT substr(agent_id,1,8) AS agent8, count(*) AS rows_n,
       sum(input_tokens) AS input_sum, sum(output_tokens) AS output_sum
FROM agent.agent_message_token_usage
WHERE created_at <= 1793779463 AND agent_id IN (/* the 63 scope ids in agents.csv */)
GROUP BY substr(agent_id,1,8) ORDER BY agent8
```

Checkpoint discovery:

```sql
SELECT job_id, source_path FROM scheduler.jobs WHERE source_path LIKE '%pdlvds%';
SELECT worker_agent_id, worker_history_agent_id, count(*) AS runs_n,
       min(started_at_utc) AS first_ts, max(started_at_utc) AS last_ts
FROM scheduler.job_runs WHERE job_id='pdlvds-progress'
GROUP BY worker_agent_id, worker_history_agent_id ORDER BY runs_n DESC
```

The series export is the same `agent_id IN (...)` list with
`SELECT created_at, agent_id, input_tokens, output_tokens
... ORDER BY created_at, agent_id`.
