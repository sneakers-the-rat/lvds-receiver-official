## Semantics — what a row is

Evidence gathered while building this export:

- A row aggregates **all model requests made while producing one message**
  in that agent. The main agent has 482 rows in this snapshot, one per
  delivered message/turn
  (a turn with many tool calls makes many requests, each re-sending the
  context — hence rows larger than the 350k context window).
- Every **completed subagent has exactly one row**, timestamped at its
  completion, totalling its whole run (e.g. the CI-fix rounds 1–2 worker:
  9,121,511 input / 45,386 output in a single row) — with one exception:
  for a subagent whose session was compacted, the row covers only the
  segment since the last compaction (input-split section; coordinator
  #1), so a compacted agent's recorded total is a floor, not a full
  accounting.
- **Running agents have no rows.** At snapshot time the second build
  coordinator (~5.5 h of v6/Freerouting work) and this metrics worker had
  none — their usage lands only when they complete. All totals here
  therefore *undercount* in-flight work.
- Sanity anchor: one live request of the root agent on 2026-11-04T07:58Z
  was estimated at 219,814 input tokens (session status) — a single
  request, vs 235,111,727 cumulative input over its 482 message rows.

## Input split — NEW vs REPEATED (ESTIMATE, not a record)

**Headline, with its error attached:** of the 724,505,183 recorded
input tokens, 602,936,034 (83.2%) were estimable. The split is
published under two bounds for the injected preamble (see the
simplification note below). **Pessimistic** (preamble never
cache-served): an estimated **57.22% (345,013,960) were NEW** —
content sent for the first time in its context window, plus the
preamble at every request — and **42.78% (257,922,074) were
REPEATED** — context re-sent within the same window. **Optimistic**
(preamble cache-served after its first send per session): **97.35%
repeated**. Per scope (pessimistic / optimistic repeated): chat tree
**48.76% / 98.26%** (of its estimable
488,970,170); checkpoint cron
**17.11% / 93.48%** (of its estimable 113,965,864). The remaining 121,569,149 tokens (16.8%) are NOT estimable (below); they
are carried as repeated in the CSV, flagged per row. Validation:
against held-out agents the estimator's reconstructed totals land at
median recorded/estimated ratio **1.06** (p10 0.46, p90 1.48; median
absolute error **14.8%** after a train-derived correction) — a much
wider spread than the fit quality on the earlier, smaller snapshot,
so read the percentages as carrying a wide uncertainty band, not as
exact. This split is the closest available proxy
for cached-vs-uncached input: repeated content is what a prompt
cache serves, but a repeat is not necessarily a cache *hit* (caches
expire), and no billing conclusion follows from tokens alone.

### Correction (2026-11-04): the compaction rule

The first published version of this estimate handled compactions
under an incorrect rule. It kept a kept item's identity alive across
a compaction: only the summary counted as new at the first request
after the boundary, and kept items went on accruing REPEATED from
that first send. That is not how a prefix cache works. A prompt
cache is keyed on the exact token prefix of a single context window;
a compaction starts a new window whose text — the summary plus the
kept items, the kept items now standing at new positions behind
different preceding text — matches nothing already cached. On the
first request after a compaction, everything in the surviving
context is therefore uncached (NEW); repeats accrue only from the
second request in the new window onward. No evidence shows any
provider preserving cache across a compaction, and systems that
expose the mechanism (Claude Code after a recompaction, for one)
treat the new window as new. The old rule measured *content
repetition* — whether the same text had ever been sent before —
which is an upper bound on the cache-served share, not the share
itself.

Effect on the numbers: NEW rises by 35,500 tokens overall
(4,780,664 → 4,816,164; REPEATED 127,876,475 → 127,840,975), so the
repeated share moves 96.40% → 96.37% of estimable input and the
chat-tree share 97.52% → 97.49%; the cron scope contains no
compactions and is unchanged. Per agent: the root agent's NEW rises
28,213 → 79,055 (three compactions in its transcripts at
publication); build coordinator #1's NEW *falls* 58,608 → 43,266,
because the old pipeline additionally carried a manual add-on that
counted its final segment's starting context on top of the summary
— a double count the corrected rule makes unnecessary, since the
segment's first request now counts the whole window exactly once,
by the rule itself. The cost summary's estimated-share sensitivity
moves with the corrected shares (Muse $44.31 → $44.39, Claude
$44.67 → $44.77, OpenAI $123.20 → $123.37; its headlines do not
depend on the split and are unchanged). Validation of the totals
model never depended on the split rule, and re-running it
reproduces every published fit statistic exactly (held-out median
ratio 1.03; median absolute error 3.5% raw, 3.2% after correction);
every published record still satisfies new + repeated = recorded
exactly, and the recorded total is unchanged at 133,253,984.

One artefact of re-running on a live machine: the regenerated
validation file lists an eighth compaction anchor — the root agent
compacted again at 2026-11-04T10:47:56Z, after the frozen export.
Its segment contains no frozen usage rows, so it changes no
published figure; the seven anchors of the original publication are
unchanged.

### Simplification (2026-11-05): the preamble split is published as two bounds

The fitted preamble — the runtime-injected standing context:
system prompt, tool schemas, and the standing files (AGENTS.md,
MEMORY.md, the alignment synthesis, indexes), fitted at roughly
68K–85K tokens per request depending on agent class, about a fifth
of the context window — is the estimate's biggest unknown, because
whether a provider's cache actually serves it cannot be observed
from any record here. At the project owner's direction the split is
therefore published under **two bounds**:

- **Pessimistic** (the headline split): the preamble is NEW at
  **every** request — every context starts totally fresh. The
  standing files are re-injected per request and are edited mid-run
  (MEMORY.md changes during ordinary work; the alignment file
  regenerates nightly), and cache residency across the long gaps
  between messages is not assumed.
- **Optimistic** (the rule this estimate originally used): the
  preamble is NEW once per session and cache-served at every later
  request — as much caching as the model allows.

Effect at this snapshot: the overall repeated share is **42.7%
pessimistic / 97.4% optimistic**; the main chat's is **37.1% /
99.2%**. Because the preamble is re-sent on every one of an agent's
requests, it dominates the NEW side of the pessimistic bound for
long-running agents. The totals model and its validation are
untouched — only the split moved.

### Why this is an estimate

The per-request table `agent.token_usage` has exactly the right
column (`cached_input_tokens`) but contains **zero rows** in this
deployment (re-verified 2026-11-04), and the per-message table has
no cache split. `agent.context_items` / `agent.context_text_segments`
have no token-count fields either (checked against the schema docs).
What does exist per item is the transcript text
(`~/agents/agent-<id>/sessions/*.jsonl`, present for all 50 agents
with usage rows), so the split is reconstructed from text sizes.

### Method (estimate_input_split.py)

- A transcript is an ordered item stream. A model *request* is
  inferred as one maximal run of consecutive assistant-produced items
  (thinking / commentary / tool calls / assistant messages); its
  input is a fixed preamble (system prompt + tool schemas, absent
  from transcripts) plus all context items present before the run.
- An item is NEW at the first request that sends it, REPEATED at
  every later send; the preamble (injected standing context) is
  split under two bounds — NEW at every request (pessimistic) or
  NEW once per session (optimistic); see the simplification note
  above. Item size
  = text character count.
- **Fork slices:** spawned chat agents' transcripts open with a
  byte-identical copy of a slice of the parent's stream (detected:
  a ≥20-item prefix also present in an earlier-born chat-tree
  transcript; found in 12 sessions, 43–361 items, 69,735–472,983
  chars). The slice is the agent's starting context (new at its
  first own request); the parent's requests inside it are not
  counted as the child's.
- **Compactions** (`compaction_checkpoint` records, 7 at
  publication): a compaction starts a NEW context window. The
  summary replaces all items before `first_kept_seq` and dropped
  items are gone; at the first request of the new window the ENTIRE
  surviving context — summary and kept items alike — counts as NEW
  (uncached), because a prefix cache is keyed on the exact prefix of
  one window and the new window's prefix matches nothing cached.
  From the window's second request on, its content accrues REPEATED
  normally. (The first published version of this bullet described a
  different rule; see the correction note above for why it was
  wrong.)
- **Single-row agents with compactions** are modelled on their
  post-last-compaction segment only: build coordinator #1's row
  reconciles with its final segment (estimated 2,276,625 vs recorded
  2,224,018, ratio 0.98) but not with its whole stream (~55M
  predicted, 25× the record) — its usage evidently accumulated over
  the final segment only. The segment's starting context counts as
  new at its first request — by the compaction rule itself (the
  segment opens a new window), not by any add-on.
- Responses are assigned to usage records by timestamp (a response
  belongs to the first record completing after it). 74 inferred
  responses fall after their agent's last snapshot record (the root
  agent kept working past the snapshot bound) and are excluded.
- Fit, per class (root / chat-tree subagent / cron worker):
  `recorded ≈ S/cpt(class) + preamble(class)·K`, K = inferred
  requests in the record, S = summed context chars before each
  request, fitted by non-negative least squares. Thinking items are
  counted as re-sent context (the with-thinking variant beat the
  without-thinking variant on held-out data, 3.2% vs 3.8% median
  absolute error — a narrow margin; both fits are in the validation
  file).

Fitted parameters (full-data fit; train-half fit in parentheses):
chars/token 3.39 (3.39) root, 3.42 (3.61) chat-sub, 3.62 (3.63)
cron; preamble 74,392 (74,392) root, 58,711 (61,326) chat-sub,
46,036 (45,754) tokens cron. These preambles are *effective* values:
they absorb per-request wrapper overhead as well as the true
system prompt and tool schemas, so do not quote them as prompt sizes.

### Validation

Split-half by agent (stratified by scope; root always in train —
it holds 102 of the 151 records; the published fit uses all agents):

- Train (124 records): median ratio 0.985, p10 0.950, p90 1.029,
  median absolute error 2.6%.
- Held-out test (17 records): median 1.028, p10 0.806, p90 1.090,
  median absolute error 3.5%; after per-class corrections derived
  on train only (0.984 root / 0.966 chat-sub / 1.003 cron): median
  1.025, median absolute error 3.2%. (Corrections cancel in the
  published proportions; they validate the totals model only.)
- The root agent's 102 records under the full fit: median 0.984,
  p10 0.952, p90 1.028, median absolute error 2.6%.
- Per-agent median ratios across the 40 estimable agents span
  0.77–1.10. Worst: build coordinator #1 (0.77) and one of its
  workers (0.79) — see the anchor cross-check for why.
- **Compaction anchors (independent cross-check):** the runtime's
  own `tokens_before` at each compaction vs the model's estimate of
  the same context: root 0.99 / 1.04 / 0.99 (within ±4%), coordinator
  #1 1.06, then 1.38 / 1.40 / 1.28 — its later, code- and
  JSON-dense segments carry more tokens per character than the
  class factor assumes. (`tokens_after` measures the compacted
  content alone and does not reconcile with the request model; it
  is not used.)
- **Not estimable:** the 10 cron run/delivery agents (596,845
  recorded input). Their session files hold the paired worker's
  stream, not their own requests: reconstructing those files
  over-predicts their ~50–70k records by ~8× (ratio ≈ 0.12). They
  are excluded from fitting and from the split percentages, and
  flagged in `input_split.csv`.

### Limitations

- Chars-per-token varies with content (prose vs code vs JSON); the
  per-class factor is an average, and dense segments (coordinator
  #1's later work) are under-estimated by up to ~40% at the segment
  level. Agent-level medians stay within 0.77–1.10, but treat any
  single record's split as ±10–20%, and small records as noisier.
- Mid-session context expiry/summarisation of old tool outputs, if
  the runtime does any outside compaction records, is invisible in
  transcripts and would inflate the repeated estimate.
- Published per-record new+repeated equals the recorded input
  exactly by construction (proportions applied to records); the
  estimation error lives entirely in the proportion.

## Caveats

- The table is **live**: the root agent keeps accruing rows. This snapshot
  ends at the 2026-11-04T08:29:34Z row; later exports will be larger.
- Coverage starts at the first row, **2026-11-03T18:34:31Z**, ~6 minutes

- Because subagent rows land at completion, token growth appears in lumps

  cumulative total of rows timestamped ≤ the commit time: work that was
  in flight at commit time is missing from that row and appears later.
- GitHub's server-side merge commits are not in this clone's HEAD lineage
  and carry no content changes; the alignment covers the 110 content

- Board state is parsed from the audit file **as committed at each
  revision** (an attempt-specific `results/audit-*.txt` when the commit
  touched one, else `results/pcb-audit.txt`). No ERC report is committed
  anywhere in the history (ERC reports live in CI artifacts), so
  `erc_errors` is `not recorded` throughout — the ERC story (875 → 0) is
  in `docs/00-status.md`, not in git.

## Cost summary (list-price equivalents)

Subscriptions are different for all three providers and unquantifiable
from any record available here. This project ran on a Muse
subscription — the user's known flat cost — and no per-token charge is
exposed in any record. The figures below are therefore **rough cost
estimates for if one would want to scale up**: the recorded token
volume priced at each provider's published pay-as-you-go API list
rates. They are not a bill, and not what this project cost.

Why API prices are the comparison currency (project owner's framing,
2026-11-04): Anthropic's and OpenAI's subscription tiers carry no
token count at all — Anthropic's are flat multipliers (5×, 20×) of an
undefined base amount, and OpenAI's are similar, except that hitting
the limit degrades your thinking level first. Only Muse's
subscription tiers correspond to an actual token count. A
subscription therefore cannot answer "what would this workload cost
to run as a business"; the pay-as-you-go API rates can, which is why
this table uses them. The report gives these costs per provider:
**all-uncached** (every input token at the standard rate — no cache
credit at all), **all-cached** (every input token at the cache-read
rate — the unattainable opposite bracket), and between them a
**cache-adjusted estimate published as two bounds** — pessimistic
and optimistic — which bills input per the estimated
new-vs-repeated split (input-split section: repeated share of
estimable input is 42.7% pessimistic / 97.4% optimistic at the
current snapshot). The split is an estimate
reconstructed from transcripts, not a measurement — no record of
actual cache hits exists — and "repeated" is an upper bound on
"cache-served": the estimate assumes every repeat of earlier context
is served from the provider's cache, modelling no cache expiry,
eviction, or minimum-prefix rules. Treat the cache-adjusted figure
as optimistic; a real cache-billed cost would land somewhere between
it and the all-uncached figure.

Two cautions on these percentages. First, they are shares of the
*estimable* input only; the not-estimable remainder (records whose
transcripts could not be reconciled with their recorded totals,
plus scheduler delivery agents) is carried as repeated by
convention in the cost figure, and is shown here rather than hidden
inside the percentage. Second, "repeated" counts content re-sent
inside one context window; a real prompt cache additionally expires
and evicts, so the cache-served share of a live run would be lower
— by how much, no available record can say. Cache *write* charges, where a provider has them
(Anthropic 1.25×/2× of base input; OpenAI 1.25× on these models),
are not modelled, so a real cache-heavy bill would land between
the tier-matched total and the cache-adjusted figure.

Why even these equivalents are rough:

- **Model attribution.** `agent.agents.model` is populated for all
  269 project agents, but only with internal codenames: the 212
  root-class agents (this chat's root plus the checkpoint cron's
  worker and run agents) record `ipnext/watermelon-v0`, and the 57
  subagents record `ipnext/avocado-5.17-v1` or
  `ipnext/avocado-5.17-v2`. Model codenames (confirmed by the project
  owner, 2026-11-04): `ipnext/watermelon-v0` = Muse Wonder;
  `ipnext/avocado-5.17-*` = Muse Spark. No Anthropic or OpenAI
  model name appears in any project record; transcript session
  headers carry no model field, and `runtime.requests` has no model
  column at all. So no project agent was served by a non-Muse model
  — the Anthropic and OpenAI columns are equivalents for comparison,
  priced per codename share at the like-for-like tiers, not records
  of spend.
- **Compaction floor.** For a subagent whose session was compacted,
  the recorded usage row covers only the segment since the last
  compaction (proven on coordinator #1 in the input-split work), so
  the recorded totals — and every cost figure here — are a floor
  for such agents, not a full accounting.
- **Steering context.** Meta's Model API token counts exclude
  Meta-injected steering context (it is not billed); the local
  records this table is built from may include injected context.
- **OpenAI long-context pricing.** Prompts over 272K input tokens
  bill at 2× input/cache and 1.5× output for the full request on
  GPT-6 Astra. This project's recorded turns include per-message
  input aggregates well above that, but the aggregates cannot
  separate individual request sizes, so the headline uses standard
  rates throughout; an identical workload actually billed by OpenAI
  would cost more than the $1,365.87 flagship upper bound.
- **Tokenizer differences.** Anthropic's pricing page notes its
  current tokenizer produces roughly 30% more tokens for the same
  text than its predecessor; the counts here were metered on Muse,
  so identical text would meter somewhat higher on Claude.

## Staying in sync during the project

The database export (`token_series.csv` / `agents.csv`) can only be
refreshed by an agent with `muse.db` access — no shell, git hook, or
CI job can reach the Muse runtime database. Everything downstream of
the export, however, is plain local computation, and it is wired to
stay in sync on its own:

- `metrics/sync_metrics.sh` re-runs the local generators
  (`align_commits.py`, `make_token_chart.py`, `make_cost_summary.py`)
  and stages the regenerated artifacts. The milestone plot the site
  shows is rendered at site-build time from `commit_alignment.csv`, so
  it follows automatically.
- `.githooks/pre-commit` and `.githooks/post-merge` (enabled per clone
  with `git config core.hooksPath .githooks`) call it — but a full run
  costs ~30 s, so the script only does work in clones that opt in with
  `git config metrics.sync true`. That flag is set in the merge clone
  (`pdlvds-split`) only; worker clones return instantly and pay
  nothing.
- The parent agent refreshes the database export as part of every
  merge to `main`, then the hook regenerates the rest. Net effect:
  metrics on `main` are never more than one merge behind the work;
  between merges the token axis plateaus at the last export, which the
  plateau in the per-message chart makes visible rather than hiding.
- The input split (`estimate_input_split.py`) needs the agent
  transcripts and a manual transcription into this README, so it stays
  an agent-run milestone step, not part of the hook.

## Regenerating at project end

CI cannot reach this database. An agent with `muse.db` access re-runs the
SQL below, rewrites `token_series.csv`/`agents.csv`, then runs
`python3 metrics/align_commits.py .`, re-renders the progress chart from
`commit_alignment.csv` (attempt commits only), and re-renders the
per-message chart with `python3 metrics/make_token_chart.py .`. Re-check the rates in
`metrics/api_rates.json` against their source pages, update rates and
fetch dates together, then run `python3 metrics/make_cost_summary.py .`.
Update the snapshot date and totals in this file and in
`docs/00-status.md`.
The input split additionally needs the agent transcripts, so it can
only be regenerated on this machine: after the re-export, run
`python3 metrics/estimate_input_split.py .` and transcribe the new
validation numbers from its output / `input_split_validation.json`
into the input-split section above.

This snapshot: `ipnext/watermelon-v0` × 49 agents,
`ipnext/avocado-5.17-v1` × 17 agents. Per-codename usage totals with
the same bound reproduce the split the cost summary prices
(watermelon 67,519,404 in / 258,026 out over 35 agents with rows;
avocado 65,734,580 in / 408,578 out over 15):

```sql
SELECT a.model, count(DISTINCT u.agent_id) AS agents_with_rows,
       sum(u.input_tokens) AS input_sum, sum(u.output_tokens) AS output_sum
FROM agent.agent_message_token_usage u
JOIN agent.agents a ON a.agent_id = u.agent_id
WHERE u.created_at <= 1793780974
  AND (u.agent_id IN (SELECT descendant_id FROM agent.agent_ancestors
        WHERE ancestor_id='4925d244-018c-4b4f-9fad-7b3ad78af7c1')
       OR u.agent_id = '4925d244-018c-4b4f-9fad-7b3ad78af7c1'
       OR u.agent_id IN (SELECT worker_agent_id FROM scheduler.job_runs
                         WHERE job_id='pdlvds-progress')
       OR u.agent_id IN (SELECT worker_history_agent_id
                         FROM scheduler.job_runs
                         WHERE job_id='pdlvds-progress'))
GROUP BY a.model
```

Checkpoint discovery:

```sql
SELECT job_id, source_path FROM scheduler.jobs WHERE source_path LIKE '%pdlvds%';
```
